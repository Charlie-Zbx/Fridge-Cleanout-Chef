# 正式评估与证据记录

当前的软件回归、公开照片探索、真实模型小批联调分别记录，均不替代下面的正式评估。所有未开展的项目保持 pending；空白不是零错误。不预设 Agent 优于基线。

## 配方与场景冻结

先审核5–10道试用配方，最终约30道；完成用量、基础人数、1–5人耗时、厨具、分批说明与来源核对。实做5组，覆盖1人、2人、至少一种3–5人和一次分批制作。结构校验通过不等于人工审核或味道验证。

冻结场景时保存配方版本和完整上下文。若沿用现有 artifacts/benchmark-v2-contexts.json，报告必须注明它使用开发估计；配方改动后另存新冻结文件，重新核对 expected，不混合两个版本的结果。场景预期由团队在看模型输出之前确定。

## 三组真实模型对照

- 单次回答：同一份库存、偏好和配方，只允许1次模型请求。
- 工具但不重规划：真实MCP，首次检查失败后停止，最多6次请求。
- 完整Agent：真实MCP与反馈重规划，最多6次请求。

每场景最多13次请求，20场景最多260次。按场景分批授权，先做小批确认驱动和记录，再开展剩余批次。运行前明确场景编号、上传内容、最多请求数、输出上限和批次时限；不以旧批次的剩余额度继续。失败或时限到达保留部分结果，不自动重试。

准备检查：`python scripts/benchmark_live.py --suite artifacts/benchmark-v2-contexts.json --case-ids 01,02` 只打印dry-run，实际调用0次。该两场景批次上限26次，默认整批420秒；`--approve-max-calls`必须与选定场景数×13完全一致，且真实调用开关仍须单独启用。只有得到该批授权后才能添加执行参数。本轮未授权任何真实对照批次。

主指标：可行任务完成率（expected=ready且最终通过独立检查 / expected=ready任务数）；硬条件违反率（声称ready但检查失败 / 声称ready数）；冲突修复率（首次检查失败但最后通过 / 首次检查失败数）；状态是否符合预期；每任务耗时及输入/输出token。分母为0时写N/A。重复运行的场景不能当作独立任务；报告失败和超时，不能只留下成功结果。按实际账单或当次价格另算费用，token数不等同实际金额。

现有“一人→五人→20分钟”连续任务另作需求变更案例，不冒充20个独立场景。检查工具发现、参数拒绝、错误传递和最终证据一致性用自动化测试单列。确定性全库无解终止与模型自主修正分别描述。

## 照片10组

使用团队本人或获许可的照片；逐组注明是否允许上传模型。每组1–3张，至少覆盖整箱、分层、可计数物品、净含量、开封、无重量依据、遮挡、跨图重复、同类独立包装、账实不符。给同一实物分配相同 object_id，并记录 independent_fridge_code，避免把多视角误算成独立冰箱。

先称重/点数并记录包装信息，再运行模型。真实总数、照片可见数、包装净含量与实际剩余量分别填写。看不见的内容不要求模型猜对；应检查它是否要求人工补充。

保留原始输出与解析结果，逐项标注漏识别、误分类、可见计数错误、标签错误、重复合并错误、无依据数量建议、人工修改次数和确认耗时。错误数写明评价分母；没有真值的公开图只做定性分析。模型响应成功不等于识别正确。已验证的人为确认逻辑不能被写成模型准确率。

## 3–5名熟人试用

流程：盘点照片 → 核对并保存 → 规划 → 修改人数或时间 → 确认实际消耗。实做后的扣减才记为真实消耗；演练使用测试厨房并注明模拟。

记录完成情况、用时、人工修改、求助次数和原话反馈。参与者编号代替姓名；先说明照片会上传模型、不做安全食用判断、可随时退出。主持人只解释任务，不代为点击、不引导评价。异地手机试用需在受限部署和额度确认后进行。
